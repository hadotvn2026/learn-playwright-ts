05 Kiến trúc & Thiết kế

Mô hình Page Object Model (POM) & Playwright Fixture

Thiết kế theo mô hình Page Object Model: Tách biệt cấu trúc UI, hành động (Actions) và kịch bản kiểm thử (Test Specs) kết hợp Fixture để tái sử dụng tối đa, giảm code trùng lặp và bảo trì dễ dàng khi UI thay đổi.

📐 Sơ đồ kiến trúc & luồng hoạt động 💻 Mapping code chi tiết

📐 1. Sơ đồ kiến trúc & Luồng hoạt động (POM + Fixture)

1. Tách biệt quan tâm

Không lẫn lộn Locator & Test Logic

File spec chỉ tập trung vào nghiệp vụ (business flow) và assert kết quả. Toàn bộ selector gom vào Page Object class.

2. Dễ bảo trì (Maintainable)

Thay đổi UI chỉ sửa 1 nơi duy nhất

Khi ID nút bấm hoặc input thay đổi (ví dụ #username sang #user_login), chỉ cần sửa 1 dòng trong LoginPage.

3. Playwright Fixture

Khởi tạo tự động & dọn dẹp an toàn

Nhờ base.extend, fixture { loginPage } được inject trực tiếp vào từng test case, loại bỏ boilerplate new LoginPage(page).

💻 2. Mapping Code chi tiết

Chuyển hóa từ sơ đồ kiến trúc sang 3 file mã nguồn thực tế trong dự án.

1. Page Object Class (login.page.ts): Khai báo các thuộc tính Locator trong constructor và các hàm nghiệp vụ (goto, login, getFlashmessage).
pages/login.page.ts TypeScript 
import { Page, Locator } from '@playwright/test';

export class LoginPage {
    readonly page: Page;
    readonly usernameInput: Locator;
    readonly passwordInput: Locator;
    readonly loginButton: Locator;
    readonly flashMessage: Locator;

    constructor(page: Page) {
        this.page = page;
        this.usernameInput = page.locator('#username');
        this.passwordInput = page.locator('#password');
        this.loginButton = page.locator('button[type="submit"]');
        this.flashMessage = page.locator('#flash');
    }

    async goto() {
        await this.page.goto('https://the-internet.herokuapp.com/login');
    }

    async login(username: string, password: string) {
        await this.usernameInput.fill(username);
        await this.passwordInput.fill(password);
        await this.loginButton.click();
    }

    async getFlashmessage() {
        return await this.flashMessage.textContent();
    }
}
2. Playwright Fixture Extension (base.ts): Mở rộng base.extend<MyFixtures> để đóng gói việc khởi tạo new LoginPage(page) thành fixture dùng chung toàn bộ test suite.
pages/base.ts TypeScript 
import { test as base } from '@playwright/test';
import { LoginPage } from './login.page';

type MyFixtures = {
    loginPage: LoginPage;
};

export const test = base.extend<MyFixtures>({
    loginPage: async ({ page }, use) => {
        // Tự động khởi tạo instance LoginPage truyền vào từng test
        const loginPage = new LoginPage(page);
        await use(loginPage);
    }
});

export { expect } from '@playwright/test';
3. Clean Test Spec (login.pom.spec.ts): Import test, expect từ base.ts. Fixture { loginPage } được tự động inject vào hook và test case.
tests/login.pom.spec.ts TypeScript 
import { test, expect } from '../pages/base';

test.describe('Heroku App - Login with POM and Fixture', () => {
    test.beforeEach(async ({ loginPage }) => {
        await loginPage.goto();
    });

    test('login with valid credentials', async ({ loginPage }) => {
        await loginPage.login('tomsmith', 'SuperSecretPassword!');
        const messageText = await loginPage.getFlashmessage();
        expect(messageText).toContain('You logged into a secure area!');
    });

    test('login with invalid credentials', async ({ loginPage }) => {
        await loginPage.login('invalidUser', 'invalidPassword');
        const messageText = await loginPage.getFlashmessage();
        expect(messageText).toContain('Your username is invalid!');
    });
});

🤖 Sơ đồ luồng Agentic Testing trong vòng đời một thay đổi code

📋 1. Copy prompt — biến mọi test fail thành ngữ cảnh AI hiểu ngay

Playwright ≥ 1.51

Từ bản 1.51, mỗi lỗi trong HTML Report, Trace Viewer và UI Mode đều có nút Copy prompt. Bấm một cái là có ngay prompt đã điền sẵn: thông điệp lỗi cộng toàn bộ ngữ cảnh cần để sửa. Prompt chỉ nằm trong clipboard — Playwright không gửi code của bạn lên server nào.

Vấn đề

Log locator khó đọc

Chuỗi locator lồng nhau + diff chuỗi dài khiến việc tự đọc message mất 10–20 phút mỗi lần fail.

Giải pháp

Ngữ cảnh tự đóng gói

Playwright đã có sẵn error, code, test info — chỉ cần đóng gói lại theo định dạng LLM đọc được.

Kết quả

Root cause trong vài giây

AI chỉ đúng dòng sai (thường là typo dữ liệu hoặc assertion lệch) và gợi ý đoạn fix cụ thể.

Prompt gồm 4 phần cố định: (1) chỉ dẫn cho AI, (2) thông tin test, (3) chi tiết lỗi kèm expected / received, (4) source code thật của spec. AI không nhận log thô mà nhận ngữ cảnh đã được sắp xếp.
Prompt structure — Copy prompt (Playwright 1.51) Markdown 
## Instructions
You are a senior test automation engineer. Explain why this Playwright test
failed, be concise, follow Playwright best practices, and suggest a code fix.

## Test info
- Test: verify max due person name
- File: tests/table.spec.ts:24:5
- Project: chromium · Retries: 1 · Duration: 5.2s

## Error
Error: expect(received).toBe(expected)

Expected: "Jason Doe"
Received: "Franklin Doe"

Call log:
  - expect.toBe with timeout 5000ms
  - waiting for locator('table#table2 tbody tr')

## Source
```ts
test('verify max due person name', async ({ page }) => {
  await page.goto('/tables');
  const rows = page.locator('table#table2 tbody tr');
  const people: { name: string; due: number }[] = [];
  for (let i = 0; i < await rows.count(); i++) {
    const row = rows.nth(i);
    const name = (await row.locator('td:nth-child(2)').textContent()) ?? '';
    const due = parseFloat(((await row.locator('td:nth-child(4)').textContent()) ?? '').replace('$', ''));
    people.push({ name: name.trim(), due });
  }
  const max = people.reduce((a, b) => (a.due > b.due ? a : b));
  expect(max.name).toBe('Jason Doe');
});
```

⚠️ Prompt chỉ đúng khi ngữ cảnh trong test còn đủ. Nếu bạn che dữ liệu hoặc tách logic ra helper quá xa, hãy đính kèm cả file helper trước khi hỏi AI.

Nút Copy as Prompt nằm ở 3 nơi: UI Mode (tab lỗi của test), Trace Viewer (thanh dưới cùng), và HTML Report (khối lỗi của test fail). Luồng dưới đây dùng UI Mode vì cho phép xem trace + sửa code ngay.
  1. Chạy UI Mode để watch file và mở test fail ngay khi vừa chạy xong.
  2. Đọc tab Error / Call log để xác định đây là lỗi assertion, locator hay timeout.
  3. Bấm Copy as Prompt — Playwright gom error + source + test info vào clipboard.
  4. Dán vào agent (Cline, Claude Code, Copilot Chat…) kèm câu hỏi bằng tiếng Việt nếu muốn.
  5. Áp fix + chạy lại: UI Mode tự re-run khi file thay đổi, xác nhận xanh trước khi commit.
Terminal Bash

# 2. Chạy trực tiếp một case đang fail để lấy ngữ cảnh sạch

import * as fs from 'fs';
import * as path from 'path';

type Entry = {
  spec: string;
  cases: string[];
  routes: string[];
  pageObjects: string[];
  tags: string[];
  risk: 'high' | 'medium' | 'low';
};

// Quét chính source of truth: mọi file spec trong tests/
const specDir = path.join(process.cwd(), 'tests');
const entries: Entry[] = [];

for (const file of fs.readdirSync(specDir).filter((f) => f.endsWith('.spec.ts'))) {
  const source = fs.readFileSync(path.join(specDir, file), 'utf-8');

  const cases = [...source.matchAll(/TC\d{2}(?:\.\d+)?/g)].map((m) => m[0]);
  const routes = [...source.matchAll(/goto\(\s*['"`]([^'"`]+)['"`]/g)].map((m) => m[1]);
  const pageObjects = [...source.matchAll(/from\s+['"]\.\.\/pages\/([\w.-]+)['"]/g)]
    .map((m) => `pages/${m[1]}`);
  const tags = [...source.matchAll(/@[a-z-]+/g)].map((m) => m[0]);

  entries.push({
    spec: `tests/${file}`,
    cases: [...new Set(cases)],
    routes: [...new Set(routes)],
    pageObjects: [...new Set(pageObjects)],
    tags: [...new Set(tags)],
    risk: pageObjects.length > 0 ? 'high' : 'medium',
  });
}

fs.writeFileSync('test-map.json', JSON.stringify(entries, null, 2));
console.log(`✅ Đã sinh test-map.json cho ${entries.length} spec`);

}

const codeDiff = diffText();

// ---------- Tầng 1: rule tất định ----------
const picked = new Map<string, string>();

for (const entry of map) {
  const hitByPageObject = entry.pageObjects.some((po) => files.includes(po));
  const hitBySpec = files.includes(entry.spec);
  if (hitByPageObject) picked.set(entry.spec, 'POM thay đổi → mọi spec import nó đều bị ảnh hưởng');
  if (hitBySpec) picked.set(entry.spec, 'Spec bị sửa trực tiếp trong PR');
}

// Smoke luôn chạy dù diff không chạm tới
for (const entry of map) {
  if (entry.tags.includes('@smoke')) picked.set(entry.spec, 'Smoke set: luôn chạy trên mọi PR');
}

// ---------- Tầng 2: LLM chấm cho các spec còn lại ----------
const ambiguous = map.filter((e) => !picked.has(e.spec));

const judged = await Promise.all(
  ambiguous.map(async (entry) => {
    const { answers } = await client.systemOne({
      state: [
        `Changed files:\n${files.join('\n')}`,
        `Diff (trích):\n${codeDiff}`,
        `Spec đang xét: ${entry.spec}`,
        `Routes liên quan: ${entry.routes.join(', ') || 'không rõ'}`,
        `Test cases: ${entry.cases.join(', ')}`,
      ].join('\n\n'),
      questions: {
        impact: choice('PR này có khả năng làm fail spec trên không?', {
          AFFECTED: 'Diff chạm vào luồng/route/assertion mà spec này đang kiểm thử',
          NOT_AFFECTED: 'Không liên quan trực tiếp, chạy thêm chỉ tốn thời gian',
          UNSURE: 'Không đủ dữ kiện để kết luận, nên chạy để an toàn',
        }),
      },
    });

    const decision = answers.impact;
    return { spec: entry.spec, choice: decision.choice, confidence: decision.confidence };
  })
);

for (const j of judged) {
  // Fail-safe: chỉ bỏ qua khi AI tự tin cao rằng không ảnh hưởng
  if (j.choice === 'NOT_AFFECTED' && j.confidence >= 0.8) continue;
  picked.set(j.spec, `AI: ${j.choice} (confidence ${j.confidence})`);
}

// ---------- Xuất kết quả ----------
const specs = [...picked.keys()].sort();
fs.writeFileSync('regression-selected.txt', specs.join('\n'));
console.log(`🎯 Đã chọn ${specs.length}/${map.length} spec:`);
for (const [spec, reason] of picked) console.log(` - ${spec}  ← ${reason}`);

⚖️ Ngưỡng confidence >= 0.8 là "công tắc an toàn": AI chỉ được phép loại bỏ test khi rất chắc chắn; mọi trường hợp mơ hồ đều mặc định chạy. Không bao giờ để agent tự ý giảm phạm vi kiểm thử khi độ tin cậy thấp.

🔍 5. AI Review Agent — soi Playwright test PR như một senior reviewer

PR bot · rubric

Con người review test thường chỉ soi "chạy xanh chưa". Agent review soi được cả những thứ tinh vi hơn: test có phụ thuộc thứ tự không, locator có dễ vỡ không, assertion có thật sự kiểm chứng hành vi không, có hardcode secret không, có vi phạm POM không. Điểm mấu chốt: agent phải chấm theo rubric cố định — nếu không, mỗi lần review sẽ cho một kết quả khác nhau.

BLOCKER Hardcode credential / token trong spec
BLOCKER Dùng waitForTimeout để "chờ cho chắc"
BLOCKER Không có assertion nào kiểm chứng kết quả
WARN Locator theo vị trí / class dễ đổi
WARN Test phụ thuộc thứ tự hoặc state của test khác
WARN Logic UI lặp lại thay vì đẩy vào Page Object
INFO Thiếu tag @smoke / @regression
INFO Thiếu nhánh âm (invalid / empty / boundary)
Review chỉ có giá trị khi nó chặn được merge xấu — nhưng không làm chậm người viết test. Vì vậy agent chỉ comment và gắn nhãn, không tự sửa; BLOCKER thì mới fail check.
  1. Trigger: PR mở/cập nhật và có file khớp tests/**/*.spec.ts hoặc pages/**.
  2. Thu thập ngữ cảnh: diff của PR, toàn bộ file sau khi sửa, và kết quả Playwright JSON report của lần chạy CI.
  3. Chấm theo rubric: agent đọc skill best practices rồi soi từng hạng mục, ghi rõ dòng + lý do.
  4. Đăng comment: gộp thành một comment có severity, kèm suggested diff — không spam từng dòng.
  5. Gate: có BLOCKER → fail check, bắt buộc sửa; chỉ WARN/INFO → comment advisory, không chặn.

## Ngữ cảnh được cung cấp
- Diff của PR (chỉ file test/page object)
- Nội dung đầy đủ của các file bị thay đổi
- Kết quả JSON của lần chạy Playwright gần nhất (để biết test có flaky/retry không)

## Rubric (bắt buộc chấm đủ, im lặng = bỏ sót)
BLOCKER  · secret/credential hardcode trong spec
BLOCKER  · waitForTimeout hoặc sleep thủ công
BLOCKER  · test không có assertion kiểm chứng kết quả
WARN     · locator dựa vào vị trí, class, hoặc text dễ đổi
WARN     · test phụ thuộc thứ tự / dùng chung state với test khác
WARN     · lặp lại chuỗi thao tác UI thay vì dùng Page Object/fixture
WARN     · assertion quá lỏng (toBeVisible cho thứ cần toContainText)
INFO     · thiếu tag @smoke / @regression
INFO     · thiếu case âm hoặc boundary

## Nguyên tắc trả lời
1. Chỉ nêu vấn đề trong phần diff của PR, không "cải tạo" code cũ ngoài phạm vi.
2. Mỗi vấn đề phải có: file, dòng, severity, lý do 1 câu, và đoạn code thay thế.
3. Đề xuất phải dùng API Playwright đúng (expect auto-retry, getByRole, test.step).
4. Không bịa dòng không tồn tại. Nếu thiếu dữ liệu, ghi "cần xác nhận".
5. Trả về DUY NHẤT một khối JSON theo schema:
   { "summary": string, "verdict": "APPROVE" | "REQUEST_CHANGES",
     "findings": [{ "file": string, "line": number, "severity": "BLOCKER"|"WARN"|"INFO",
                    "rule": string, "message": string, "suggestion": string }] }

🧩 Verdict nên là REQUEST_CHANGES nếu có BLOCKER; nếu chỉ có WARN/INFO thì APPROVE kèm comment — tránh biến agent thành "cảnh sát" khiến team tắt bot.

Comment phải đọc được trong 30 giây. Có tóm tắt, có verdict, rồi bảng finding sắp theo severity — người viết test biết ngay phải sửa gì để PR đi tiếp.

// Với mỗi test fail, reporter đã lấy được { test, rootCause, confidence } từ jevTriage
switch (result.rootCause) {
  case 'ASSERTION':
    // Test assert sai / dữ liệu đổi → KHÔNG tự sửa code, cảnh báo cho người
    await sendSlackAlert(result.test, result.rootCause, result.confidence);
    break;

  case 'LOCATOR_ISSUE':
    if (result.confidence >= 0.85) {
      // 1. Ghi system prompt ép agent chỉ được sửa locator trong Page Object
      fs.writeFileSync(`ai-triage-logs/${cleanName}-instruction.txt`, instructionPrompt);

      // 2. Gọi agent không tương tác — agent đọc DOM rồi mở PR fix
      execSync(`claude --prompt-file ${promptPath} --auto-approve`, { stdio: 'inherit' });
    } else {
      console.log(`⚠️ Nghi LOCATOR_ISSUE nhưng confidence thấp → QA review.`);
    }
    break;

  default:
    console.log(`🔍 Cần manual review: ${result.test}`);

Nightly Digest

Tóm tắt kết quả chạy đêm: bao nhiêu fail, nhóm theo root cause, test nào mới flaky, so với hôm qua — gửi vào Slack/Teams bằng Block Kit.

Dấu hiệu cần: report dài, không ai đọc hết.

scripts/flaky-report.ts — nền tảng dữ liệu cho Flaky Hunter TypeScript 
import { defineConfig, type Reporter } from '@playwright/test';
import * as fs from 'fs';

// Reporter tích luỹ kết quả mỗi lần chạy vào 1 file JSONL để phân tích xu hướng
export default class FlakyTracker implements Reporter {
  private results: { title: string; status: string; retries: number; duration: number }[] = [];

  onTestEnd(test, result) {
    this.results.push({
      title: test.titlePath().join(' › '),
      status: result.status,
      retries: result.retry,        // retry > 0 nghĩa là lần đầu đã fail
      duration: result.duration,
    });
  }

  async onEnd() {
    const line = this.results.map((r) => JSON.stringify(r)).join('\n');
    fs.appendFileSync('test-results/history.jsonl', line + '\n');

    const flaky = this.results.filter((r) => r.retries > 0);
    if (flaky.length) {
      console.log(`🌀 ${flaky.length} test cần retry — ứng viên Flaky Hunter:`);
      for (const f of flaky) console.log(` - ${f.title} (retry ${f.retries})`);
    }
  }
}

📈 Dữ liệu lịch sử là tài sản: test-results/history.jsonl cho phép agent tính tỉ lệ flaky theo thời gian và chỉ đề xuất quarantine khi có đủ bằng chứng, thay vì "đoán theo một lần fail".

Agent giỏi việc lặp lại, dở việc quyết định thay con người. Bảng này là "hợp đồng" nên thống nhất trong team trước khi bật bất kỳ automation nào.

✅ Nên giao cho agent

  • Sinh test plan, sinh spec từ plan, refactor codegen thô.
  • Debug khi có ngữ cảnh đầy đủ (Copy prompt, trace, HTML report).
  • Sửa locator trong Page Object khi UI đổi.
  • Chọn tập test regression theo PR diff (kèm guardrail).
  • Review PR theo rubric và gợi ý diff cụ thể.
  • Phân loại nguyên nhân fail, tóm tắt báo cáo chạy đêm.

🚫 Không giao cho agent

  • Quyết định expected value nghiệp vụ (giá, quyền, trạng thái đơn).
  • Tự merge PR do chính agent tạo.
  • Đổi assertion để test xanh mà không có người duyệt.
  • Bỏ qua / giảm phạm vi test khi confidence thấp.
  • Đụng tới dữ liệu production hoặc credential thật.
  • Được cấp quyền ghi rộng hơn mức cần thiết trong CI.

🎯 Tóm lại: Playwright's Agentics không phải "để AI viết test hộ", mà là dùng agent cho đúng ba việc — sinh nhanh, chọn đúng, sửa kịp — còn con người giữ phần quyết định điều gì là đúng. Bắt đầu nhỏ: bật Copy prompt cho cả team trước, rồi init-agents cho planner/generator, sau đó mới tới regression selector và reviewer.
